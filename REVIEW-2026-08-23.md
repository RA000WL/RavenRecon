## 3. Findings

Severity distribution: **3 HIGH · 9 MEDIUM · 14 LOW · 12 INFO.**

### HIGH

#### H-1 (HIGH, §0.6 violation) — Crawl caches an all-failed run as `StatusCompleted` empty corpus → permanent cache poisoning
- Where: `internal/crawl/katana.go` — `KatanaSource.Crawl`; error swallow at
  :233–241 and :262–264; unconditional store at :280–301.
- Problem: per-host runner errors and non-zero exits fold into Diagnostics;
  nothing counts host failures. The result is then stored **unconditionally**
  as `cache.StatusCompleted` whenever cache+version exist — including when
  every host invocation failed and `URLs` is empty. The cache serves only
  completed records (`internal/cache/cache.go:216–219`), default TTL is
  infinite: one broken run (katana crash, network down) permanently serves
  the cached empty URL set as authoritative for that domain/scope/depth/
  version key.
- Why it matters: a FAILED outcome is persisted and replayed as COMPLETED —
  exactly what the fixed outcome vocabulary exists to prevent. No test covers
  this cache path.
- Independently confirmed by lead reviewer (code read end-to-end).
- Fix: track per-host outcomes; skip the store or store
  `StatusIncomplete`/`StatusFailed` when ≥1 host execution failed (mirror
  discovery's `statusToCache`). Add hermetic regression tests with a fake
  failing runner: all-fail ⇒ no completed record ever written.

#### H-2 (HIGH, §0.7 violation) — Ingest stage deadlocks forever on cancellation
- Where: `internal/pipeline/adapt/import.go:278–297` (`ingestStage.Run`),
  interacting with `internal/runtime/pool.go:403–424` (`workerLoop`).
- Problem: the join is an external `sync.WaitGroup` whose `Done()` lives only
  inside the job closure (:283). On ctx cancellation, pool workers exit
  immediately and queued-but-unpicked jobs are dropped WITHOUT executing
  their Func (documented pool behavior); their `wg.Done()` never runs, so
  `wg.Wait()` (:297) blocks forever — before the deferred `pool.Shutdown`
  (:270) can execute. The whole pipeline, and thus Ctrl-C during
  `ravenrecon ingest`, hangs indefinitely whenever more files are queued than
  picked up instantly (default queue 64 ≫ concurrency 4; rate limiting
  widens the window arbitrarily).
- Evidence: empirically reproduced by review session (temp test: cancel
  150 ms into a 40-file ingest → `pipeline.Run did not return within 10s`);
  code path independently confirmed by lead reviewer. Existing tests miss it
  because tiny files finish before the race window opens.
- Fix: drop the WG as join point — submit all jobs, then
  `pool.Shutdown(budgetedCtx)` (its forced path always waits to zero), then
  fold, treating still-zero `outcomes[i]` as cancelled. (Or guarantee Done
  outside the Func via a counted done-channel drained after Shutdown.)
- Note: H-2 also masks honest cancellation reporting for dropped files.

#### H-3 (HIGH) — `filterIngestURLs` silently drops every imported URL with an explicit non-default port
- Where: `internal/pipeline/adapt/import.go:819–831`.
- Problem: it feeds canonical `u.HostPort` directly into `asset.NewHost`.
  `HostPort` retains explicit ports (`example.com:8080`, pinned by
  `internal/asset/url_iszero_test.go:80–88`), while
  `validateHostname` (`internal/asset/normalize.go:71–77`) rejects `:` in
  labels → error → silently skipped. Every URL from httpx/Burp/ZAP/CDX/WARC/
  katana/plain imports on a non-standard port never reaches the corpus: no
  counter, no flag, stage stays `completed`. Applies identically to cache-hit
  replays, so the loss is stable and invisible across runs. Downstream stages
  lose exactly the non-standard-port attack surface.
- Independently confirmed by lead reviewer (both sides of the contract read).
- Fix: strip the port before the host check (reuse the correct sibling
  helper `urlHost` in `httpprobe.go:403–418`), keep the full URL asset. Also
  see L-9 (three divergent copies of this filter).

### MEDIUM

#### M-1 (MEDIUM, §0.6) — secrentel `Overflow` flag false-negative after Phase-2 dedup shrink
- Where: `internal/secrentel/engine.go:376` (`processDocument`) derives
  `Overflow = len(candidates) >= maxCandidates` post-hoc; cap trips at
  `internal/secrentel/scan.go:159–163` (per-pattern) and `:232–235`
  (candidate admission); Phase-2 dedup shrink at `scan.go:263–283`; dead
  field `overflowCandidates` declared at `scan.go:51`, never written/read.
- Problem: after the candidate cap trips, Phase-2 duplicate removal can
  shrink the list below the cap → flag reads `false` although drops
  occurred. Only the raw counter preserves truth. The flag is the mandatory
  truncation signal of a full §0.6 chain (stored `record.go:90`, replayed
  `record.go:360`, merged stickily `report.go:244`, reported `report.go:117`).
- Evidence: reproduced empirically by review session (63 kept < cap 64 with
  1 dropped → engine flag FALSE); both code paths independently confirmed by
  lead reviewer.
- Fix: set `out.overflowCandidates = true` where either cap trips; derive
  `entry.Overflow = overflowCandidates || counts.OverflowDropped > 0`;
  wire up or delete the dead field.

#### M-2 (MEDIUM, §11) — urlintel cache keys omit tool version
- Where: `internal/urlintel/record.go:44–53` (`urlKey`) +
  `internal/urlintel/adapt/source.go:405–465` (`Run` detects versions, then
  discards them).
- Problem: key hashes {operation, URL identity, adapter name,
  parse_parameters} — not the detected gau/waybackurls/waymore version. A
  tool upgrade changes emitted data; per-(URL,adapter) hits serve pre-upgrade
  payloads until TTL. Contradicts the repo's own convention one layer over
  (`internal/discovery/cache.go:30–37`: version in key, unknown version ⇒
  never cached, test-pinned). Doc comment on `urlKey` claims "every input
  that materially changes the result."
- Confirmed by lead reviewer.
- Fix: thread detected version into the key (`cache.ToolInfo{Name,
  Version}`), adopt unknown-version-never-cached like discovery.

#### M-3 (MEDIUM, §11) — Crawl cache key omits Timeout / Concurrency / RateLimit
- Where: `internal/crawl/katana.go:336–354` (`crawlCacheKey` carries only
  `depth`+`scope`) vs execution shaped by `cfg.Timeout`
  (`context.WithTimeout`, :224–228), `-rl`/`-c` flags (:215–216).
- Problem: crawl output materially depends on wall-clock budget and pacing;
  a short-timeout run's smaller set is served to a later long-timeout config
  without executing. Importer demonstrates the house convention
  (`CacheKeyForFile` includes every bound).
- Confirmed by lead reviewer.
- Fix: add the three normalized values to the Config map.

#### M-4 (MEDIUM, §11) — Discovery cache keys omit QualityConfig, though the gate shapes the stored/replayed set
- Where: `internal/discovery/cache.go:30–37` (`cacheKey`) vs
  `internal/discovery/pipeline.go:404–459` (post-gate store: retained set is
  capped by `MaxPerSource` BEFORE persistence; issues replay sticky).
- Problem: records persist the producing run's post-gate retained set; keys
  do not include gate configuration. Raising `MaxPerSource` after a capped
  store silently keeps serving the smaller capped set (flagged over_cap, so
  honest — but stale w.r.t. the operator's configured gate). Same class of
  gap as M-2/M-3, different input.
- Found by lead reviewer during core read.
- Fix: include normalized QualityConfig in the key Config map, or document
  replay-over-recompute as deliberate policy with the same explicitness as
  the unknown-version policy.

#### M-5 (MEDIUM, §8 parity) — jsintel/adapt `Run` has no adapter-level execution timeout
- Where: `internal/jsintel/adapt/run.go:78` (`Run`). Only detection is
  bounded (`tool.go:348`).
- Problem: subjs/linkfinder/SecretFinder are ACTIVE fetchers whose Python
  pair has no internal HTTP timeout; the only bounds are caller ctx + output
  caps. Sibling `urlintel/adapt/source.go:143,559` enforces
  `DefaultToolTimeout=2m`. Tests pass `context.Background()`; pool permits
  `Timeout=0`; a wedged SecretFinder pins a worker until force-kill (or
  forever outside a pool). Latent today (no production caller — verified),
  but §8 wants timeouts enforced, not delegated; the wiring milestone will
  inherit whatever sits here.
- Confirmed by lead reviewer (grep: no WithTimeout on the Run path).
- Fix: wrap ctx with a per-tool default timeout (mirror urlintel/adapt)
  before orchestration lands.

#### M-6 (MEDIUM, §0.6 asymmetry) — priority `AttackPaths` silently drops paths beyond the run cap
- Where: `internal/priority/attackpath.go:153–156` (silent
  `paths[:maxPathsPerRun]`); contrast `correlate.go:189–193` which returns
  `(groups, truncated)` for the identical cut class.
- Problem: caller passing 40 qualifying groups gets 32 indistinguishable
  from "exactly 32 produced". Step-level cuts ARE flagged
  (`AttackPath.Truncated`); path-count cut has no signal. Test
  `attackpath_test.go:142–161` can't assert reporting because the API offers
  none.
- Confirmed by lead reviewer (both cut sites read).
- Fix: mirror Correlate's shape (`([]AttackPath, bool)` or result struct);
  library-only today, cheapest now.

#### M-7 (MEDIUM, latent §15) — TUI interesting-feed renders full `secret_candidate` identities (value embedded) to the terminal
- Where: `internal/tui/feed.go:178–180` uses raw `p.Identity` as display
  label; rendered verbatim `render.go:207–216`. Identity embeds the
  percent-encoded VALUE (`internal/asset/secret_candidate.go:232–237`).
- Problem: the repo's own rule (`internal/secrentel/record.go:143–153`,
  `redactedCandidateID`): the full identity "must never appear in errors or
  logs." A live feed + scrollback/transcripts is neither of its carve-outs.
  Dormant ONLY because no producer emits these events yet (verified by
  grep) — the secrentel→bus wiring milestone activates the leak.
- Confirmed by lead reviewer (both sites read).
- Fix before that milestone: render type+digest label (mirror
  `redactedCandidateID`), keep full identity only in the in-memory dedupe
  key; regression-test that rendered labels contain no value substring.

#### M-8 (MEDIUM, honesty) — Opt-in DNS brute failures report bare `completed` with no marker

#### M-9 (MEDIUM, vocabulary) — urllive outcome fold omits the `partial` bucket

## 5. Verdict

**BLOCK**

Three HIGH findings stand verified; two are direct §0 violations:
H-1 violates §0.6 (failed results persisted and replayed as `completed`
through the persistent cache), H-2 violates §0.7 (cancellation does not
terminate the ingest stage — an indefinite user-facing hang, reproduced
empirically). Per review policy, any §0 violation forces BLOCK regardless
of otherwise-exemplary engineering quality.

The fixes are small and localized: (H-1) outcome-aware store decision +
regression tests; (H-2) replace the WaitGroup join with pool.Shutdown-based
join; (H-3) strip ports via the existing correct helper. M-1..M-9 should
follow in the same hardening wave; each has a concrete fix in its entry.

Recommended order: H-2 → H-1 → H-3 → M-1 → M-7 (before secrentel→bus
wiring) → remaining §11 key fixes (M-2/M-3/M-4) → M-5 before jsintel/adapt
orchestration → the rest.
